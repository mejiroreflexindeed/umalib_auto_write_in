# 06 · 实际数据库副本只读证据基线

## 1. 调查对象与安全边界

本页记录 2026-08-29 对用户明确提供的实际数据库**副本** `main-copy.db` 的只读调查结果，用来约束后续 UmaLib Adapter 与 Database Writer 的设计。

- 文件大小：`82,296,832` 字节
- 文件 SHA-256：`4e152ea33e046b1bd238387c39fa32ad4dc6fd584d5fc1f6c1ff10431a6a54dc`
- Schema 指纹：`d7b1966992e75819e37d41ae9c091ec21c2cdf9c5b6727af78f95398d0179aa8`
- SQLite `user_version`：`0`
- 页大小 / 页数：`4096 / 20092`
- 检查前后文件哈希、大小、mtime 与目录文件集合完全相同；未产生 `-wal`、`-shm` 或 `-journal`。

调查只输出结构、计数和格式特征，不复制文章标题、正文、作者、译者或来源内容。该副本仍然不是 Writer 的测试靶；在正式 Writer 阶段必须再生成候选副本并使用事务、回读与回滚边界。

## 2. Schema 与完整性结论

- 核心契约匹配：`article`、`tag`、`tagged` 与发行包 Prisma Schema 一致。
- 核心行数：`article=6983`、`tag=405`、`tagged=17471`。
- 其他行数：`creator=2`、`rec=115`、`dict=24`。
- `PRAGMA integrity_check`：`ok`。
- 外键违规：`0`。
- 重复 `tagged(articleId, tagId)` 关联：`0`。
- 实际检查没有 blocker，只有一个“同名标签” warning。

这证明当前副本适合继续做 Adapter 设计证据，但**不等于已经批准 Writer 写入**。

## 3. 标签证据

标签类型数量：

| `tag.type` | 数量 | 从现有名称观察到的主要用途（仅为证据归纳） |
|---:|---:|---|
| `0` | 48 | 内容属性、分级或通用标记 |
| `1` | 203 | 角色 |
| `2` | 65 | 系列、设定或作品集合 |
| `3` | 85 | 长篇作品或合集标题 |
| `4` | 4 | 敏感或争议内容标记 |

这些语义是从实际数据分布归纳出的工程线索，不应在没有产品确认时固化成自动联动规则。

发现一组真实同名标签：

| 名称 | ID | 类型 | 当前关联数 |
|---|---:|---:|---:|
| `王牌x(仁子)T` | `428` | `0` | `2` |
| `王牌x(仁子)T` | `429` | `0` | `0` |

因此后续 Adapter 必须遵守：

1. 同名命中多个标签时不得自行选择；
2. 不得因为名称存在重名就再自动新建第三个同名标签；
3. UI/计划中要暴露候选 ID、类型和必要统计，让人工选择；
4. 新标签的类型必须由明确规则或人工选择提供，不能从字段名随意推断。

文章标签数量分布：中位数 `2`、P90 `5`、P95 `7`、P99 `9`、最大 `21`、平均 `2.50`；有 `37` 篇文章没有标签。这说明“至少一个标签”不是数据库层面的硬约束。

## 4. 来源字段证据

`article.source` 是单一可空文本字段，现有数据把多个来源压平成空格分隔的 token：

- 每篇 token 数中位数 `1`，P90/P95 为 `2`，最大 `7`，平均 `1.26`；
- 统计到 `https` token `7776` 个、`http` token `16` 个；
- 另有 `1009` 个无法按绝对 URL 识别的相对或非标准 token；
- 高频来源域包含 NGA、Pixiv、tsumanne 等。

因此不能仅凭现有数据库反推出“原作系列、原作、译作系列、译作”的业务优先级。TASK-007 只允许把人工明确选定且排序后的来源确定性压平；默认优先级要等产品规则确认后再加入。

## 5. 正文与 Quill HTML 证据

`article.content` 是 HTML，而不是纯文本。6983 篇正文全部非空；长度中位数约 `2930` 字符、P95 约 `14359`、最大 `305328`。

按文章计数的格式特征：

- 含内联颜色：`472`
- 含背景色：`4`
- 含 `ql-*` class：`840`
- 含图片：`1692`
- 含注释定义形态：`464`

实际出现的常见 HTML 标签包括 `p`、`br`、`img`、`span`、`strong`、`blockquote`、标题、列表、`a`、`sup`、`pre` 等；常见属性包括 `src`、`class`、`style`、`width`、`height`、`href`、`target`、`rel`、`alt`。未观察到事件属性，但未来实现仍必须采用允许列表，不能把上游 HTML 原样信任。

主要 Quill class 包括：

- `ql-align-justify`、`ql-align-right`、`ql-align-center`
- `ql-indent-1` 等缩进等级
- `ql-size-large`、`ql-size-small`
- `ql-syntax`
- `ql-cursor`（编辑器残留，应作为清理候选而非业务格式）

颜色主要使用 `color: rgb(...)`，也存在命名颜色及全角括号等历史非标准写法。不能为了“清理”而未经兼容测试批量改写旧内容。

当前 `ApprovedSubmissionPackage` 只携带 `body_text`，不携带 NGA 原始 HTML、BBCode 或结构化富文本。于是：

- TASK-007 可以安全实现“纯文本 → 最小 Quill HTML”的确定性渲染；
- TASK-007 不能声称保留了 NGA 颜色、图片或富文本；
- 要真正保留这些格式，必须在未来扩展上游采集/交接契约，并用真实 NGA 格式样本建立允许列表和转换测试。

## 6. 对下一阶段的直接约束

下一阶段先生成**纯内存、可复核、不可执行 SQL 的变更计划**：

```text
ApprovedSubmissionPackage
        + 人工 AdapterChoices
        + 目标标签目录快照
        ↓
UmaLibChangePlan（ready / blockers / warnings / 稳定哈希）
```

该阶段应做到：

- 唯一同名标签可确定性复用；多重命中必须阻断并等待选择；
- 未命中标签只有在人工明确指定类型后才进入“计划新建”；
- 系列字段不自动猜 `tag.type`；
- 来源只按人工明确顺序压平；
- 正文只把纯文本转成转义后的最小 Quill HTML；
- 不打开数据库、不输出 SQL、不复制数据库、不实现 Writer。

等这份变更计划模型通过验收后，才能把候选副本、事务写入和写后回读作为独立的后续任务。

## 7. 当前证据仍不能回答的问题

- 四类来源的最终优先级和允许缺失规则；
- `[系列]` 应映射 `tag.type=2`、`3`，还是由人工按场景选择；
- 标签联动的正式业务表；
- NGA 实际返回的 HTML/BBCode、颜色和图片字段形态；
- `article.note` 应由人工填写、保持空值，还是采用现有软件的摘要算法；
- 新文章 `uploadTime` 应取投稿、批准还是最终导入时间；
- Writer 是否还需同步任何核心三表之外的数据。

这些问题必须继续保持为显式选择或 blocker，不能让编码代理自行补成“看起来合理”的规则。
